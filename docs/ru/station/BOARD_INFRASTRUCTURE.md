# Station / BOARD: реализованная серверная инфраструктура

## Область поставки

Этот этап добавляет установку и серверные контракты, **не новый дизайн и не новый веб-интерфейс**. Существующие HTML/CSS/JavaScript не переписаны. Пока пользовательский интерфейс не подключён, `/` возвращает JSON с адресами API.

Обработка: существующий SatDump -> настоящие `_annotated_presentation.png` и/или `_annotated_minimal.png` с JSON -> рабочая публикация -> атомарное переименование -> `public/items` -> `/api/v1/board`. Полный научный результат остаётся в приватном `archive`. Метаданные presentation сохраняются целиком: время наблюдения не заменяется mtime, ориентация и калибровка не додумываются сервером.

## Установка

В проверенном полном бинарном Station-пакете выполните `sudo ./install.sh`. При наличии терминала запускается мастер: каталог -> IPv4 -> порт -> сервер -> источник -> тип -> итоговый план и подтверждение. Enter принимает значение, `b` возвращает назад, `q` отменяет. Цвет не является единственным обозначением результата; индикатор показывает активность, не выдуманный процент. `NO_COLOR`, `--no-color`, `--no-animation` и `TERM=dumb` поддерживаются. Для SSH/CI используется чистый текст.

```bash
sudo ./install.sh --yes
sudo ./install.sh --non-interactive --listen 0.0.0.0 --port 8090 \
  --source-path /mnt/receiver/presentation --source-kind image
./install.sh --dry-run --allow-compatible
```

Последняя команда только показывает план на стенде. Она не устанавливает программу и не проверяет runtime/systemd. Для внешнего источника мастер включает маркер готовности: `имя.png.ready` для image и `.ready` внутри законченного каталога product. Файлы без маркера не обрабатываются; через API можно осознанно переключить `require_ready` на false и использовать окно стабильности `settle_seconds`.

Автоматически создаются `satdump-worker`, `satdump-web`, `satdump-control`. Они включаются в автозапуск, запускаются и проверяются. При nginx также создаётся внутренний `satdump-board`. Проверяется не только HTTP 200: нужны heartbeat обработчика, схема каталога BOARD, ответ авторизованного API и отказ API без токена.

Ошибки активации возвращают предыдущие код, настройки и unit-файлы. Снимок находится в `/opt/satdump-station/rollback-state`; данные/БД этим откатом не возвращаются. Созданные системные пользователи и пустые каталоги не удаляются автоматически. `--no-start` допускается только на остановленной станции и не подтверждает работоспособность.

```bash
sudo satdump-station doctor
sudo satdump-station logs
sudo satdump-station rollback
```

`doctor` запускается от пользователя обработчика, проверяет конфигурацию, доступность источников, место и наличие launcher. Сообщение `ismount=false` не доказывает отсутствие сетевого ресурса: вход может быть подкаталогом монтирования. Полную приёмку входов и мандатных политик Astra выполняют отдельно.

## Выбор сервера и ОС

По умолчанию — встроенный сервер на отдельном Python/Pillow из офлайн-пакета, без дополнительных сетевых зависимостей. Он ограничивает число соединений и предоставляет только разрешённые маршруты. Это профиль локальной станции/доверенной ЛВС, **не общедоступный интернет-сервис**.

`--web-server nginx` использует уже установленный `/usr/sbin/nginx` в отдельной непривилегированной службе с собственной конфигурацией; системный `/etc/nginx` не включается и не изменяется. Установщик проверяет `nginx -t`. Если nginx отсутствует, выводится понятная ошибка; скрытого apt/pip нет. API управления не проксируется в незащищённую ЛВС.

Современный Uvicorn требует Python >=3.10; базовый legacy runtime этого проекта — Python 3.5. Поэтому Uvicorn не добавлен ценой замены системных библиотек. Основание: https://pypi.org/project/uvicorn/ (проверено 09.09.2026). nginx умеет отдельную конфигурацию и проксирование: https://nginx.org/en/docs/beginners_guide.html.

Целевой бинарный профиль: Astra 1.6 x86_64, glibc224. Astra 1.5/1.7 не объявляются совместимыми этим установщиком даже с `--allow-compatible`: для них нужен другой пакет/приёмка. Никаких замен системной glibc, отключения мандатного контроля, прав 777 и установки Docker на станцию нет.

## Управление конфигурацией будущим интерфейсом

Контракт: `config/station/board-openapi.json`. Публичные методы: `GET /api/v1/board`, `GET /api/v1/board/status`. Управляющие методы на loopback-порту 8091: `GET /api/v1/control/health`, `/config`, `/capabilities`; `POST /validate`; `PUT /config`.

Все управляющие запросы требуют `Authorization: Bearer ...`. 256-битный токен создаётся один раз в `/etc/satdump-station/control.token`, не печатается и не попадает в журналы. Для удалённой работы — SSH-туннель либо отдельно согласованный HTTPS-прокси. Не передавайте токен через URL, не добавляйте его в исходники будущего сайта. `Host` и `Origin` проверяются; CORS на произвольные домены не включён.

Основной сценарий клиента: GET config/ETag -> изменить `settings` -> POST validate -> показать предупреждение о повторной обработке -> PUT config с `If-Match` и при необходимости `confirm_reprocess: true` -> следить за `applied_revision` в публичном status. HTTP 202 означает сохранение, не немедленное применение. При конфликте 412 нужно перечитать конфигурацию, а не перезаписать чужие изменения.

Редактируются источники в root-разрешённых каталогах, тип входа, маркеры готовности, включение источников, параметры очереди/лимиты; presentation-выходы, ориентация, подписи, темы макетов; autogen существующих пресетов и выражения каналов; фильтры/макеты/лимит BOARD. Реальные приборы и названия пресетов читаются из установленного движка и возвращаются в capabilities.

Идентификаторы конвейеров разрешены root-политикой, по умолчанию — конвейеры исходной station.json. Безопасные argv ограничены samplerate/baseband_format/dc_block/iq_swap/freq_shift; API не принимает произвольную команду. Lua, исполняемые пути и произвольные ключи запрещены. Основной `data_dir`, бинарник, unit-файлы и системная сеть не редактируются веб-процессом. Начальный путь вывода выбирается установщиком; перенос уже существующего хранилища — отдельная административная миграция, не реализованная этим API.

Настройки сохраняются атомарно с ревизиями в `data/control`. API пишет только туда; обработчик читает, проверяет и применяет новую ревизию между заданиями. При изменении рецепта старые ожидающие задания помечаются superseded, новые вычисляются из нового рецепта; старые готовые продукты остаются. Фильтры видимости BOARD не меняют рецепт и не запускают пересчёт. Скрытие карточки **не является разграничением доступа** к ранее опубликованному URL и не удаляет файлы.

## Позднее подключение оформления

Когда появится готовая сборка сайта (каталог с `index.html`):

```bash
sudo satdump-station ui-deploy /path/to/ready-board-files
```

Команда копирует только переданный пользователем каталог, отклоняет ссылки/спецфайлы, размещает версию вне кода движка и атомарно переключает `/opt/satdump-station/board-ui/current`. Публичный WEB подхватывает файлы без перезапуска. В поставку этого этапа ни страница, ни тема оформления не включены.

Отдача статических файлов ограничена расширениями и корневым каталогом; API и приватные пути не заменяются статикой. JavaScript будущего сайта должен быть отдельным локальным файлом: политика CSP не разрешает inline-скрипты и внешние CDN. Никакого Node/npm на целевой станции не нужно.

## SSH-развёртывание

```bash
./station.sh deploy station.tar.gz operator@station -- \
  --listen 0.0.0.0 --port 8090 --web-server builtin
```

Рядом нужен `.sha256`. Проверяется безопасная структура архива, SSH host key, sudo без запроса пароля, повторная сумма на станции. Аргументы передаются раздельными данными с POSIX-экранированием. Удалённая установка использует тот же установщик, включая WEB/API/проверку запуска. Временный каталог убирается при успехе и ошибке; при недоступном SSH выводится его путь для контролируемой очистки.

## Проверки и границы подтверждения

`tests/station/test_board_infra.py`: типы/границы JSON, запрещённые пути и argv, конфликты ревизий, HTTP-авторизация и Host/Origin, псевдотерминал мастера, конфигурация nginx, права unit-файлов, публикация обоих макетов и подключение к прежнему обработчику. В интеграционных тестах вызов нативного декодера подменяется контрольным генератором; это не реальный радиоприём.

Полная готовность бинарного релиза требует дополнительно сборки glibc224-пакета, установки с настоящим systemd на Astra 1.6 без сети, контрольной записи, отказов обновления и проверки после перезагрузки. Прохождение Python/Bash-тестов не заменяет эту приёмку.
