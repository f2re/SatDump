# 🛡️ 07 · Эксплуатация, обновление и резервирование

[← Галерея](WEBSITE.md) · [Оглавление](README.md) · [Сборка и выпуск →](BUILD_RELEASE.md)

Синхронизация и UTC: [настройка часов и диагностика](UTC_AND_SCHEDULER.md).

## 1. Службы и пользователи

| Служба | Пользователь | Доступ |
|---|---|---|
| `satdump-worker.service` | `satdump-station` | Чтение входов; запись состояния, рабочих файлов, журналов, архива и публикации |
| `satdump-web.service` | `satdump-web` | Публичный сайт; в варианте nginx также собственный временный каталог `/run/satdump-web` |
| `satdump-control.service` | `satdump-control` | Авторизованный API; запись настроек в `data/control`, без доступа к сырым данным |
| `satdump-board.service` | `satdump-web` | Внутренний HTTP-сервер, только при использовании nginx |

Код принадлежит root. Активные конфиги создаются с ограниченными правами. Воркер не запускается от root, веб-пользователь не получает доступ к приватному архиву. Установщик создаёт systemd-ограничения, включая отдельный временный каталог и запрет повышения привилегий; у воркера включён `PrivateNetwork=true`.

Это не запрет чтения уже смонтированной ОС сетевой папки, но сам процесс не должен заниматься её монтированием или скачиванием файлов. Доступ и политики Astra проверяются отдельно.

```bash
sudo systemctl status satdump-worker satdump-web satdump-control --no-pager
sudo satdump-station status
sudo satdump-station logs
```

`logs` выводит последние 100 строк и продолжает наблюдение; выйти можно Ctrl+C. Подробный вывод отдельного декодирования находится в `logs/<job_id>.log`, а предыдущая попытка — в `.log.previous`.

## 2. Регулярная проверка

| Что проверить | Признак нормы | Неочевидный риск |
|---|---|---|
| Службы | Все установленные службы активны | Активный процесс не равен успешной обработке |
| Очередь | Новые задания переходят в `done` | `done` может быть частичным; проверяйте `processing_quality`. `failed` требует устранения причины и `retry` |
| `/health.json` | Свежий heartbeat и ожидаемые источники | HTTP 200 возможен при мёртвом воркере |
| Входной диск | Смонтирован ожидаемый ресурс | Пустая точка монтирования может выглядеть как пустой источник |
| Место | Есть запас под вход и результаты | `max_items` ничего не удаляет |
| Контрольный продукт | Правильные спутник, UTC, геометрия, легенда | Оценка выполняется по данным и паспорту, не только по изображению |

```bash
df -h /var/lib/satdump-station
sudo du -sh /var/lib/satdump-station/{inbox,work,archive,public,logs}
findmnt /mnt/receiver
```

При пользовательском `data_dir` замените путь. `findmnt` приведён для примера сетевого входа.

Отчёт `logs/<job_id>.quality.json` содержит полноту набора; `/health.json` передаёт краткий `last_result`. Карантин не очищается автоматически. Для МТВЗА и обязательных приборов используйте [порядок диагностики](MTVZA_PROCESSING.md).

## 3. Обновление пакетом

Скачайте и проверьте **новый бинарный пакет**, сохраните резервную копию, распакуйте в отдельный каталог, затем запустите его `sudo ./install.sh`. Не копируйте отдельный новый Python-файл поверх активной версии.

Установщик проверяет внутренние SHA-256, окружение и движок, размещает версию в `releases`, переключает `current` и при обычном запуске проверяет обработчик, веб-службу, управляющий API и состояние очереди. Предыдущая версия запоминается в `previous`. Настройки и наблюдения не заменяются содержимым пакета; рядом кладутся новые `.example`.

> [!WARNING]
> Предусмотренный откат при провале проверки запуска — **не полная транзакция любых шагов установки**. Ошибка до проверки может оставить созданные каталоги, пользователей или часть служебных файлов. Сохраните журнал и диагностируйте причину; не считайте неуспешную установку отсутствием любых изменений.

`--no-start` предназначен для подготовительного размещения. Он не проверяет работоспособность и не является горячим обновлением. На работающей станции сначала остановите службы; дальнейшее включение выполняйте осознанно.

## 4. Откат

```bash
sudo satdump-station rollback
sudo systemctl status satdump-worker satdump-web satdump-control --no-pager
sudo satdump-station status
```

Восстанавливаются предыдущие код, файлы конфигурации, активная ревизия API и состояние служб из снимка установщика. Научный архив, публикации и SQLite-очередь не откатываются. Перед возвратом к старому пакету проверьте совместимость форматов данных. Для восстановления исторического набора снимков нужна резервная копия.

Сам бинарный Desktop-релиз Astra 1.7 и каталоги станции Astra 1.6 не смешиваются при откате.

## 5. Резервная копия

Сохраняются конфигурация, очередь, публикационные и научные данные, а также проверенный бинарный архив установленной версии. Одного `queue.sqlite3` при работающем WAL недостаточно для произвольного копирования: используйте согласованное резервирование или остановите воркер.

**Пример с остановкой обработчика и управляющего API для стандартных путей.** Укажите существующее хранилище резервных копий вне каталога данных и убедитесь в свободном месте. Веб-служба остаётся доступна для чтения.

```bash
(
  set -e
  BACKUP="/srv/backups/satdump-$(date -u +%Y%m%dT%H%M%SZ)"
  sudo install -d -m 0700 "$BACKUP"
  sudo systemctl stop satdump-worker.service satdump-control.service
  trap 'sudo systemctl start satdump-worker.service satdump-control.service' EXIT
  sudo tar -C / -czf "$BACKUP/config-and-data.tar.gz" \
    etc/satdump-station var/lib/satdump-station
  sudo cp /opt/satdump-station/current/PACKAGE-MANIFEST.json "$BACKUP/"
)
```

При ином `data_dir` измените список архивируемых путей. Это резервирование может быть объёмным; пример не задаёт автоматическую ротацию. Восстановление сначала проверьте на отдельном стенде: остановленные службы, соответствующий код, восстановленные владельцы/права, затем проверка запуска и контрольного продукта. Не распаковывайте резервную копию поверх работающей очереди без плана восстановления.

## 6. Хранение и очистка

Автоматическая очистка не реализована. `max_items` ограничивает размер ленты, а не количество каталогов. Успешный `work` удаляется при `keep_work=false`; неуспешные задания могут оставлять рабочие копии. `archive_science=false` не удаляет ранее сохранённый архив.

Не используйте удаление `public/items` как ротацию. При следующем запуске обработчика отсутствующие/пустые файлы публикации переводят прежнее задание обратно в очередь. Неполный набор переносится в `work/quarantine-*`; восстановление возможно только из доступного исходника. Это проверка наличия и ненулевого размера, не контроль хешей каждого растра и не непрерывный мониторинг диска. Политику хранения следует реализовывать согласованно с индексом и БД; до этого используйте контролируемое архивирование, а не рекурсивное удаление по возрасту.

## 7. Права и закрытая сеть

| Ситуация | Что требуется |
|---|---|
| Приёмник пишет локальные файлы | Настроить владельца/группу/ACL у производителя, чтобы воркер мог читать новые файлы |
| Вход на SMB/NFS | Смонтировать ОС, проверить UID/GID/ACL и реальную доступность |
| Сайт нужен в ЛВС | Явный IPv4 bind, доступный порт, согласованный сетевой экран |
| Станция недоступна с GitHub | Доверенный runner с маршрутом или локальный SSH-деплой |
| Физически закрытый контур | Перенос проверенного архива на носителе |

Нельзя выдавать `chmod 777`, отключать проверку SSH-ключа, заменять системную glibc или ослаблять мандатный доступ только ради исчезновения ошибки. Старые Python/Pillow и декодеры обрабатывают только доверенные входные данные. Встроенный HTTP не предназначен для прямой публикации в интернете.

## 8. Перенос на другой диск или узел

Установщик не мигрирует существующий `data_dir`. Перенос — отдельная операция: остановка записи, согласованная копия, проверка нового пути и прав, исправление активной конфигурации и systemd-путей, контрольное включение. Старую копию не удаляют до проверки. Самостоятельное редактирование только `station.json` недостаточно, поскольку разрешённые каталоги и `RequiresMountsFor` записаны в unit-файлах.
