# UTC и автоматическая обработка файлов

[Руководство станции](README.md) · [Входные данные](INPUTS.md) · [Конфигурация](CONFIGURATION.md)

## Время наблюдения, файла и публикации

Станция использует UTC. Настройка часового пояса браузера не меняет подпись снимка. Разные виды времени хранятся раздельно:

| Поле каталога | Содержание |
|---|---|
| `acquisition_start_utc`, `acquisition_end_utc` | Начало и конец наблюдения в ISO 8601 с окончанием `Z`; `null`, если время не установлено |
| `acquisition_start`, `acquisition_end` | Те же моменты в секундах Unix |
| `acquisition_time` | Подпись для человека: `15.09.2026 · 10:00:00–10:15:00 UTC` |
| `acquisition_time_raw` | Исходная подпись из паспорта |
| `acquisition_time_status` | `ok`, `missing` или `invalid` |
| `file_mtime` | Время изменения входного файла, секунды Unix |
| `published_at` | Время подготовки карточки станцией, секунды Unix |
| `updated_at` | Время обновления каталога или состояния, секунды Unix |

Парсер принимает ISO 8601 с явным `Z` или смещением и UTC-подписи, формируемые SatDump. Например, `2026-09-15T02:30:00+03:00` преобразуется в `2026-09-14T23:30:00Z`. В интервале через полночь указываются обе даты. Строка без часового пояса не трактуется как местное время; обратный интервал отклоняется.

Неизвестное или некорректное время наблюдения не заменяется временем файла либо публикации. Исходный JSON-паспорт не переписывается. При обновлении индекса уже опубликованные карточки получают нормализованные поля без повторного декодирования.

Карточки с известным временем сортируются по началу наблюдения, от новых к старым. Карточки без него идут после них, по времени публикации. При одинаковом времени порядок задаёт идентификатор. Пересчёт старого наблюдения не переносит его впереди новых наблюдений.

Для выгрузки МТВЗА время набора берётся из доступных бортовых отметок, не из времени запуска обработки. Отсутствующая отметка остаётся неизвестной. Точность старого преобразования бортовых счётчиков требует проверки на реальной записи. [Обработка МТВЗА](MTVZA_PROCESSING.md).

## Синхронизация часов ОС

`TZ=UTC` задаёт представление времени, но не синхронизирует часы. Его устанавливают `station.sh`, службы systemd и окружение запуска SatDump. Команда `satdump-station logs` выводит журнал с `--utc`.

Системные часы обслуживает настроенная в ОС служба: chrony, ntpd либо systemd-timesyncd. На изолированной станции источником может быть NTP-сервер локальной сети с проверенным временем или подключённый эталонный приёмник. Одновременно корректировать часы несколькими службами не следует. При отсутствии внешнего эталона точность UTC не подтверждается одним лишь работающим таймером ОС.

На установленной станции:

```bash
satdump-station time-status
timedatectl status
# Дополнительно, только при установленном chrony:
chronyc tracking
chronyc sources -v
```

`time-status` возвращает `synchronized`, `unsynchronized` или `unknown`. `unknown` означает, что получить состояние через `timedatectl` не удалось. Работающая служба NTP сама по себе не считается признаком синхронизации. `doctor` возвращает этот результат отдельно в объекте `clock`; его общий `ok` относится к проверке конфигурации, файлов и движка.

Адрес NTP задаётся в конфигурации выбранной службы ОС, а не в `station.json`. Для chrony строка имеет вид `server <адрес-доверенного-NTP> iburst`; имя файла и службы зависят от установленного пакета. После изменения проверяются выбранный источник, время последнего измерения и отклонение часов. Системный часовой пояс можно оставить местным: процессы Station выводят UTC независимо от него.

Установщик не меняет часы, аппаратные RTC, часовой пояс ОС или конфигурацию NTP. `After=time-sync.target` задаёт порядок запуска, но без действующего механизма ожидания не доказывает синхронизацию. Для архивных данных обработка не блокируется ожиданием сети; правильность времени самого наблюдения проверяется по паспорту и данным приёмника.

## Планировщик файловой очереди

Планировщик входит в `satdump-worker.service`. Это последовательный обход каталогов, а не cron-задание и не подписка inotify:

```text
sources[].path → готовность и стабильность → очередь SQLite → рабочая копия
→ SatDump → цветокомпозиции и паспорта → приватный архив + каталог сайта
```

При пустой очереди пауза между обходами равна `poll_seconds` (обычно 10 секунд). Во время обработки следующего обхода нет: новые файлы обнаруживаются после завершения текущего задания. Поэтому `poll_seconds` не является максимальным временем от поступления файла до его обнаружения.

`settle_seconds` задаёт длительность неизменности состава, размеров и времён изменения файлов. Для записей и многоканальных наборов рекомендуется `require_ready=true`: производитель создаёт `запись.cs16.ready` либо `<каталог-пролёта>/.ready` после завершения передачи. Маркер не отменяет проверку стабильности. Пути, маски, конвейер, уровень входа и параметры задаются в `sources`, а не в исходниках C++.

| `kind` | Обработка |
|---|---|
| `image` | Готовый PNG/JPEG: паспорт, обзорная копия и миниатюра; спектральный синтез не выполняется |
| `product` | Набор `product.cbor` с каналами: `satdump reprocess` |
| `pipeline` | Сырая запись или кадры: выбранный конвейер SatDump с `--offline` и `--processing_config` |

Пример `meteor_iq` в поставляемом конфиге выключен. Его можно включить только после проверки формата записи, частоты дискретизации и соответствия конвейеру. Для разных форматов нужны отдельные источники. Полный пример находится в [описании входов](INPUTS.md#pipeline).

Базовая конфигурация — `/etc/satdump-station/station.json`. При управлении через API актуальные значения находятся в `settings.station.sources` документа `/var/lib/satdump-station/control/active.json` и имеют приоритет над базовыми. Чтение и сохранение выполняются через `/api/v1/control/config` с токеном и ревизией; вручную изменять подписанный ревизией документ нельзя. Разрешённые корни задаёт администратор в `control-policy.json`. Новые настройки применяются между заданиями.

## Защита от скачков времени и повторов

Окно стабильности, тайм-аут процесса и интервалы повторных попыток измеряются монотонными часами. Коррекция системной даты вперед или назад не сокращает и не растягивает эти интервалы.

Очередь хранит монотонный срок повтора и идентификатор загрузки ОС. Перезапуск службы в пределах одной загрузки сохраняет задержку. После перезагрузки ОС ожидающие задания снова доступны для попытки; прежний счётчик ошибок сохраняется. Старые очереди дополняются полями автоматически. `next_at` остаётся справочным временем Unix, а значение `0` используется командой ручного повтора.

Проверка `worker_alive` сравнивает монотонные отметки только в пределах одной загрузки ОС. Состояние от предыдущей загрузки отвергается. Для старого формата состояния дополнительно отвергается отметка из будущего. Это проверка работоспособности процесса, а не точности NTP.

Идентификатор задания зависит от содержимого, имён входных файлов и рецепта, а не от текущей даты. Повторное сканирование неизменного завершённого задания не создаёт новый результат. Рабочая копия сохраняет время изменения входных файлов. Исходные файлы и их паспорта не редактируются.

## Проверка

Из корня исходников с Python и Pillow:

```bash
python3 -m unittest discover -s tests/station -v
```

`test_timebase.py` проверяет часовые пояса, переход через полночь, некорректные отметки, скачки часов, обновление старой очереди и запуск конвейера по маркеру. Интеграционный тест использует контрольный исполняемый файл, а не настоящий радиодекодер. Приёмка реальной станции дополнительно требует проверки NTP, контрольной записи и перезагрузки ОС.

Реализация: [время](../../../services/station/timebase.py), [очередь](../../../services/station/station.py), [BOARD](../../../services/station/board.py). Справочные материалы: [монотонные часы Python](https://docs.python.org/3/library/time.html#time.monotonic), [chrony](https://chrony-project.org/documentation.html), [systemd-timesyncd](https://www.freedesktop.org/software/systemd/man/latest/systemd-timesyncd.service.html).
