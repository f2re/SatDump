# SatDump Station — Astra Linux 1.6

## Назначение и границы

Станция принимает файлы из каталогов, сохраняет очередь, запускает SatDump, создаёт цветосинтезы и презентационные PNG/JSON, готовит небольшие превью и автоматически обновляет локальный сайт. Приём радиосигнала с SDR, скачивание внешних данных и настройка сетевых дисков — отдельные задачи; воркер наблюдает уже доступные файловые каталоги.

Три точки входа: **`station.sh` — управление; `install.sh` — установка готового пакета; `build.sh` — прежняя сборка только движка в исходном репозитории.** Прежде чем что-либо устанавливать, выполните `./station.sh help`.

Astra 1.6: x86_64, системная glibc не заменяется. Движок и отдельный Python/Pillow собираются/комплектуются в Debian Stretch с ограничением символов `GLIBC <= 2.24`. Это проверка ABI-базиса, **не сертификат совместимости с конкретной обновлённой Astra и её политиками безопасности**. Тест в Debian-контейнере не проверяет ядро Astra, мандатный доступ, сетевое монтирование и systemd целевой станции.

## 1. Готовый пакет: установка без интернета

Проверьте рядом с архивом его файл `.tar.gz.sha256`, распакуйте и откройте каталог:

```bash
sha256sum -c satdump-*.tar.gz.sha256
# Распакуйте выбранный архив, не все версии одновременно.
tar -xzf satdump-1.2.2-astra16-station-<commit>-x86_64.tar.gz
cd satdump-1.2.2-astra16-station-<commit>-x86_64
sudo ./install.sh
```

В имени замените `<commit>` на фактическую часть имени скачанного пакета. Не используйте исходный GitHub Source code ZIP вместо бинарного офлайн-пакета.

Сайт: **http://127.0.0.1:8090/**. Для доверенной локальной сети:

```bash
sudo ./install.sh --listen 0.0.0.0 --port 8090
```

Затем откройте `http://IP-СТАНЦИИ:8090/`. Установщик не открывает межсетевой экран и не меняет политики безопасности ОС. Внешний интернет не является поддерживаемым режимом публикации: для него нужен отдельно настроенный защищённый обратный прокси, TLS и аутентификация. Встроенный сервер — ограниченный read-only сервер для станции и доверенной ЛВС, без загрузки файлов или административных действий через браузер.

Пакет содержит свой Python и Pillow: на целевой машине не запускаются `apt`, `pip`, `npm`, `curl` и компилятор. Штатные Bash, coreutils, util-linux, useradd/runuser и systemd должны присутствовать. Пакет не меняет glibc, загрузчик, NSS и системные библиотеки. Старое программное окружение требует сетевой изоляции: наличие офлайн-бандла не означает отсутствие известных уязвимостей старых компонентов.

## 2. Структура установленной станции

```text
/opt/satdump-station/
  releases/<release_id>/       версии кода: engine/, runtime/, services/, scripts/
  current -> releases/...     активная версия
  previous -> releases/...    предыдущая версия для отката
/etc/satdump-station/
  station.json                источники, лимиты, очередь, пути
  processing.json             дополнения к настройкам SatDump
  web.env                     адрес и порт сайта
  *.example                   новые примеры, НЕ замена ваших настроек
/var/lib/satdump-station/
  inbox/images/               готовые PNG/JPEG
  inbox/products/<pass>/      полный набор каналов с product.cbor
  inbox/meteor_iq/             пример сырого входа; источник изначально выключен
  state/queue.sqlite3         очередь и результаты попыток
  state/worker.lock           один активный потребитель очереди
  work/<job_id>/              изолированная рабочая копия
  logs/<job_id>.log           вывод декодера; одна предыдущая попытка сохраняется
  archive/<job_id>/           сохранённые исходные/декодированные научные продукты
  public/catalog.json        атомарно обновляемый каталог сайта
  public/items/<job_id>/      только законченные PNG/JPEG/JSON и превью
```

`--data-dir /data/satdump-station` задаёт отдельный каталог при первой установке. Обновление не переносит существующее хранилище. Не помещайте входной каталог внутрь `public`, `work`, `archive`, `logs` или `state`. SQLite и `work/public` должны находиться на локальной ФС, не SMB/NFS; входы можно читать с заранее смонтированной сетевой папки. Исходные каталоги не удаляются и не модифицируются воркером.

## 3. Как подавать данные

### Готовое изображение

Скопируйте PNG/JPEG в `inbox/images/`. Воркер ждёт неизменности размера/mtime и соседнего JSON в течение `settle_seconds` (по умолчанию 30 секунд, проверка каждые 10 секунд). Надёжнее писать файл с суффиксом `.part`, затем переименовывать в окончательное имя в той же файловой системе.

Нельзя достоверно отличить законченную загрузку от загрузки, которая просто замерла на 30 секунд. Для медленных/сетевых копирований установите `require_ready: true` и создавайте `image.png.ready` последним. JSON-паспорт имеет имя `image.json` и передаётся **до** маркера.

Снимки без паспорта показываются честно: «время наблюдения не указано»; mtime файла подписывается отдельно. Ни имя спутника, ни температура, ни классификация облаков из картинки не угадываются. Оригинал остаётся неизменным; создаются только отдельные обзорные JPEG размером не более 1920×1080 и миниатюры не более 480×270, без обрезки.

### Набор SatDump с каналами

В `inbox/products/` один дочерний каталог соответствует одному пролёту:

```text
inbox/products/pass-20260908/
  dataset.json                необязателен для поиска отдельных продуктов
  MSU-MR/product.cbor
  MSU-MR/...каналы...
  ...другие приборы...
  .ready                      создаётся последним, после всех каналов
```

Воркер копирует весь пролёт в приватный `work`, находит каждый `product.cbor` и вызывает:

```bash
engine/satdump reprocess /путь/к/рабочей/копии/MSU-MR /etc/satdump-station/processing.json
```

Новая команда не обновляет TLE через сеть. Для привязки используются данные продукта; без достаточной геолокации нельзя считать ориентацию «север сверху» подтверждённой. Кеш прежнего автосинтеза отключается для рабочего объекта; исходный CBOR не меняется. Сайт принимает результат только при наличии **нового** `_annotated_presentation.png` и корректного JSON-паспорта. Старые оформленные копии в рабочем продукте удаляются до пересчёта, но остаются нетронутыми в исходном каталоге.

### IQ/кадры: явный профиль декодера

В `station.json` есть **выключенный пример** `meteor_iq` с `meteor_m2x_lrpt`, `baseband`, `s16`, 1 024 000 отсчётов/с. Это пример записи конкретного формата, а не автоматическое определение любой записи Meteor. Перед включением задайте фактическую частоту дискретизации, формат, уровень входа и остальные параметры своей записи, затем `enabled: true`.

Параметры передаются массивом `options` без оболочки. Метаданные рядом со снимком не могут задавать команды, исполняемые файлы или аргументы. После завершения передачи `pass.cs16` создайте `pass.cs16.ready`. Воркера следует использовать для доверенных входных данных: защитные лимиты не делают старые декодеры безопасными для произвольных файлов из интернета.

Для NOAA/MetOp и других декодеров создавайте отдельный источник с собственными `pipeline`, `input_level`, `patterns` и `options`. Набор доступных декодеров зависит от профиля движка `reference` или `meteor`. Универсального корректного декодера по расширению файла нет.

## 4. Цветосинтез, легенды и материалы

Формулы, LUT, калибровка и проверка наличия каналов выполняются **штатным SatDump**, а не Python-вебсервером. В `processing.json` можно дополнять `viewer.instruments.<instrument>.rgb_composites` существующими пресетами и их `autogen`, `presentation`, `project`, `geo_correct`. Используйте реальные идентификаторы приборов и пресетов из `engine/share/satdump/satdump_cfg.json`.

По умолчанию включены полное и компактное оформление. Основной сайт выбирает полное `_annotated_presentation.png`; компактные PNG и научные файлы сохраняются в приватном `archive/`. JSON-паспорт содержит спутник, прибор, продукт, время, ориентацию и семантическую легенду. На сайте доступны оригинал оформленного PNG и паспорт; физические легенды не заменяются самодельной цветовой шкалой. Предыдущие правила русских географических подписей и оформления пункта приёма остаются в движке и не переопределяются сайтом.

Растровые плашки не добавляются в геопривязанный научный GeoTIFF. Сайт использует отдельную публикационную копию. При отсутствии нужных каналов синтез может быть пропущен движком; отсутствие всех презентационных результатов считается ошибкой задания, даже если процесс вернул код 0.

Изменение рецептов требует перезапуска воркера. Хеш настроек участвует в идентификаторе задания; изменённые рецепты образуют новую версию продукта. Для принудительной переработки после изменения самого движка увеличьте `processing_revision`. Старые опубликованные версии не заменяются.

## 5. Службы, очередь и диагностика

```bash
sudo satdump-station status
sudo satdump-station logs
sudo systemctl status satdump-worker satdump-web
sudo satdump-station restart
sudo satdump-station retry --job <полный_64-символьный_ID>
```

Состояния: `pending → running → done`; при ошибке — `pending` с задержкой, затем `failed` после `max_attempts`. Изменённый во время передачи вход становится `superseded`, его новое устойчивое состояние рассматривается отдельно. После аварии задания `running` возвращаются в очередь. Блокировка `flock` не позволяет двум процессам конкурировать за декодирование. Если публикация успела завершиться до сбоя записи в БД, повторная попытка не создаёт дубликат.

Публикация: рабочий каталог → готовые PNG/JSON/превью → атомарное переименование каталога → атомарный каталог JSON. Браузер не видит частично сформированный набор. Отказ одного снимка не останавливает очередь или сайт. Исчезновение сетевого входа отображается отдельным состоянием, а не как «новых данных нет».

Два непривилегированных пользователя: `satdump-station` для обработки и `satdump-web` для HTTP. Веб-пользователь не имеет доступа к исходникам наблюдений, SQLite, приватным журналам и настройкам обработки. Воркер работает с `PrivateNetwork=true`: обновление TLE и любые обращения к внешним источникам в этом процессе недоступны. Каталоги источников должны быть читаемы сервисной учётной записью. Не выдавайте `chmod 777`; настраивайте группу/ACL и применимые политики Astra.

Лимиты задаются в `station.json`: длительность процесса, число попыток, размер входа, число пикселей, журнал и минимальное свободное место. Архив автоматически **не удаляется**. При нехватке места постановка новых входов приостанавливается; обслуживайте хранение по собственной политике. `max_items` ограничивает каталог браузера, но не объём архива на диске.

`/health.json` сообщает отдельно `web_alive` и свежесть heartbeat `worker_alive`. Работающий сайт не выдаёт остановленный обработчик за исправную станцию.

## 6. Обновление и откат

Новый готовый пакет устанавливается той же командой `sudo ./install.sh`. Проверяются файловые SHA-256 и запуск среды. Код кладётся в новый `releases/<id>`, активный `current` переключается, службы перезапускаются. Собственные настройки не заменяются; новые образцы имеют расширение `.example`. Повторная установка того же пакета допустима, несовпадение содержимого под тем же id — ошибка.

```bash
sudo satdump-station rollback
```

Откат возвращает предыдущий код, не удаляя очередь, архив или конфигурацию. Для несовместимых будущих миграций схемы БД потребуется отдельная миграционная процедура; текущая версия создаёт схему очереди 1 без разрушающих миграций. Перед эксплуатационным обновлением резервируйте `state/` и `/etc/satdump-station/` при остановленном воркере.

Однокомандная передача по SSH с машины, имеющей доступ к станции:

```bash
./station.sh deploy ./satdump-...tar.gz operator@station
```

Нужны заранее настроенные SSH-ключи, проверенный `known_hosts` и неинтерактивное право выполнить установку через `sudo -n`. Проверка ключа хоста обязательна и не отключается. Сам закрытый хост не обращается к GitHub. Для полностью изолированной станции перенесите архив носителем и выполните локальный `install.sh`. Это автоматизация установки, а не доказательство, что конкретная удалённая машина уже была обновлена.

## 7. Сборка из исходников и GitHub Actions

На подключённой к сети x86_64 Debian/Ubuntu-сборочной машине нужны `git`, `python3`, `debootstrap`, `debian-archive-keyring`, `rsync`, `binutils`, `util-linux`, `xz-utils`, `curl`, `ca-certificates`, root/sudo. Необязательная установка только на сборочном хосте:

```bash
sudo apt-get install git python3 debootstrap debian-archive-keyring rsync binutils util-linux xz-utils curl ca-certificates
./station.sh build --jobs 2
```

Сборка выполняется из чистого коммита ветки. `reference` — прежний полный CLI-профиль; `--profile meteor` — ограниченный набор Meteor/NOAA/APT. Существующие проверки/фиксации GCC, CMake и NNG в `scripts/astra/portable/` сохраняются. Новые скрипты не вводят автоматического отключения проверки подписей архива.

Результат: `dist/station/satdump-1.2.2-astra16-station-<commit>-x86_64.tar.gz`, соседний SHA-256, манифест и инструкция внутри пакета. В корне готового пакета — `START_HERE.ru.md`, `install.sh`, `station.sh`, `PACKAGE-MANIFEST.json`, `SHA256SUMS`, `LICENSE`; реализация разложена по подкаталогам. Сборка требует сети; **установка и эксплуатация готового пакета — нет**. Комплект для полной повторной компиляции без сети эта версия не обещает.

Workflow `.github/workflows/station-astra16.yml`: быстрые тесты выполняются автоматически; полная сборка включается вручную или маркером `[station-release]` в коммите. Пакет проверяется заново в чистом Stretch с отключённой сетью. Это отдельная проверка от запуска в сборочном chroot.

Публикация — отдельный prerelease с уникальным тегом прогона; прежний релиз Astra 1.7 не перезаписывается. Необязательный автодеплой доступен **только при ручном запуске** с `deploy_astra16=true`, через окружение `astra16-station` и SSH с современной сборочной машины. В окружении задаются секреты `ASTRA16_DEPLOY_TARGET` (`user@host`), `ASTRA16_DEPLOY_KEY` и заранее проверенный `ASTRA16_KNOWN_HOSTS`. Настройте подтверждение окружения и ограничьте доступ к доверенной ветке. GitHub Actions и его JavaScript-действия на самой Astra не запускаются. Целевая станция должна быть достижима по SSH с runner; для внутренней сети используйте доверенную современную машину с таким доступом или локальный `station.sh deploy`, для изолированной — носитель. Ключи, сервер и права sudo автоматически не создаются. Ручной запуск GitHub `workflow_dispatch` требует наличия workflow в default branch; пока он есть только в этой release-ветке, используйте push-коммит с `[station-release]` для сборки и локальный SSH-деплой.

## 8. Что означает проверка

`./station.sh test` выполняет синтетические тесты очереди, атомарной публикации, идемпотентности, изменения рецептов, ошибок изображений и read-only HTTP. Тестовый заменитель декодера проверяет только контракт вызова; он не является настоящей обработкой радиозаписи. Полная сборка отдельно компилирует реальный SatDump. До промышленной эксплуатации необходим прогон вашей контрольной записи на фактической Astra 1.6 с проверкой цветосинтеза, геолокации, подписей, автозапуска после перезагрузки и доступа к источникам.
