# 🎨 Стиль и сопровождение документации

## 1. Структура страницы

У страницы один H1, затем навигация «назад / оглавление / далее». Основные секции идут от пользовательской задачи к деталям: назначение → предпосылки → команды → ожидаемый результат → ограничения → ссылки на реализацию. Длинная таблица параметров живёт в справочнике, а не дублируется в пяти README.

| Материал | Каноническое место |
|---|---|
| Витрина проекта и выбор первого действия | Корневой `README.md` |
| Полная карта материалов | `docs/README.md` |
| Руководство станции | `docs/ru/station/` |
| Научная документация движка | Существующие тематические страницы `docs/ru/` |
| Релизы и доказательства | `docs/ru/RELEASES.md` |
| История изменений | Корневой `CHANGELOG.md` |
| Назначение каталога | Его собственный `README.md` |

## 2. Оформление GitHub

Используются реальные workflow-плашки с параметром ветки, сдержанная группа статических информационных плашек, таблицы выбора, Mermaid-схемы и раскрываемые ответы на частые вопросы. Эмодзи маркируют назначение секции, а не заменяют текст.

Не рисуйте статическую зелёную плашку «всё работает». Не используйте `releases/latest` как универсальную ссылку для разных семейств Astra. Название продукта и роль архива должны быть понятны до скачивания. Внешние badges могут не загрузиться без сети; смысл README должен сохраняться без них.

| Выделение | Назначение |
|---|---|
| `NOTE` | Дополнительный контекст |
| `TIP` | Удобный способ работы |
| `IMPORTANT` | Условие корректного выбора или результата |
| `WARNING` | Риск потери данных, неверной интерпретации или небезопасной настройки |

Пишите раскрываемые блоки `<details>` с пустыми строками вокруг Markdown внутри. Для важной схемы добавляйте текстовую последовательность: не все локальные просмотрщики поддерживают Mermaid.

## 3. Команды и примеры

Всегда указывайте **где выполнять**: исходники, распакованный пакет, установленная станция или машина развёртывания. Имя файла-заглушки и демонстрационный адрес должны быть явно обозначены. Команды, изменяющие систему или останавливающие службу, не смешиваются с блоком безопасной диагностики без предупреждения.

Для законченного shell-примера используйте ограду `bash`; проверяется `bash -n`, команды не исполняются. Для вывода терминала, схемы пути или метасинтаксиса используйте `text`. Для полноценного JSON — `json`; для фрагмента сначала оформите корректный объект и объясните, куда его вставлять. Не добавляйте комментарии внутрь JSON.

## 4. Точность утверждений

Различайте «написано», «проверено тестом», «собрано», «проверен автономный пакет», «опубликовано» и «испытано на целевой станции». Датированный снимок CI содержит ссылку на конкретный run/SHA. Синтаксическая проверка сайта не называется браузерной приёмкой.

Невидимые пользователю нюансы документируются: реальное значение `once`, отсутствие ротации, зависимость хеша от имён, поведение `rollback`, смысл mtime, пределы определения готовности и heartbeat. Не обещайте возможностей, которых нет в коде.

## 5. Ссылки

Для документов в репозитории применяйте относительные ссылки; для важной секции — стабильный явный якорь. Ссылки на конкретный релиз/CI должны быть абсолютными и проверяемыми. Ссылка на код в конце главы показывает основание описанного поведения.

## 6. Автоматическая проверка

**Где:** корень исходного дерева, Python 3 и Bash, без сторонних Python-библиотек.

```bash
python3 scripts/docs/check.py
python3 -m unittest discover -s tests/docs -v
```

Проверяются документы из [navigation.json](navigation.json): наличие одного H1, закрытые ограды, завершающий перевод строки, локальные ссылки и Markdown-якоря, синтаксис JSON и Bash. Ссылки внутри примеров не интерпретируются как навигация. Отсутствующая внешняя сеть не делает проверку ложнокрасной: внешние URL не запрашиваются и их доступность не утверждается.

**Границы:** это целевая проверка нового навигационного и эксплуатационного набора, не аудит каждой исторической Markdown-страницы. Mermaid не исполняется, браузерная вёрстка автоматически не подтверждается. Старые научные материалы сохраняются как дополнительные источники.

## 7. Автономная документация

```bash
python3 scripts/docs/export.py \
  --output /tmp/satdump-documentation \
  --revision "$(git rev-parse HEAD)"
python3 scripts/docs/check.py --root /tmp/satdump-documentation
```

Экспортёр копирует Markdown-руководства, разрешённые иллюстрации из `docs/assets`, лицензию и навигацию. Создаёт `README.md`, `START_HERE.ru.md`, `OPERATIONS.ru.md`; относительные ссылки пересчитываются. Ссылки на не включённые исходники закрепляются на переданном Git SHA и требуют сети. Команды внутри оград не переписываются и не запускаются.

Самостоятельный экспорт помечен как **документация, не бинарный пакет**. С `--package` тот же справочник включается упаковщиком в новый дистрибутив станции. Старые опубликованные архивы не изменяются. Отдельный workflow Documentation публикует только документационный артефакт.
